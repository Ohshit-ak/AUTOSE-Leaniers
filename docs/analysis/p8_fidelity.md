# P8: do the specs say what the requirement says?

Three parts, all on stored data (L0 v11, `runs/*/qwen-v11/rep1`, accepted specs), no model:

1. **Grounding** (deterministic): are the spec's constants taken from the requirement? Below.
2. **Gold comparison** for 25 gamma j specs: `docs/analysis/p8_gold.md`.
3. **Fidelity review** of a 60-spec sample by two people: `docs/analysis/p8_fidelity.csv` with the rubric below;
   agreement with `python evaluation/kappa.py`.

## 3. Fidelity review: sample, rubric, agreement

**Sample** (`python evaluation/p8_grounding.py --fidelity-csv docs/analysis/p8_fidelity.csv`): 60 accepted specs,
stratified by the L0.5 strength class: 24 weak, 33 strong, 3 copy-ok (population: 203 weak, 302 strong, 12 copy-ok of
517). Within a class the SRS are taken round-robin (sorted by name) and each SRS's specs in sha256(doc, id) order, so
the sample is the same on every run and spreads over the 16 SRS that have accepted specs (peering and get real 0.2
have none). 3 to 6 specs per SRS.

**Columns.** `requirement_text`, `lean_types` (fields of every structure), `lean_pre`, `lean_post` (one line each),
`auto_hint` (deterministic signals only: ungrounded constants, the copy/constant implementation that satisfies a weak
spec, L0.5 flags), then `rater1`, `rater2`: **blank, for two team members**. Rate independently, without discussing,
before reading the other column. The `auto_hint` column is a pointer, not a verdict. No model (open or closed) fills
the rater columns: the project uses open-weight models only, and a model's labels would not be a human evaluation.

**Rubric.** Judge the spec against the requirement sentence only (not the rest of the SRS, not what a good system
would do). Read `pre` as "what the spec assumes" and `post` as "what any correct implementation must guarantee".
Pick one label:

| label | meaning | example |
|---|---|---|
| `faithful` | Every condition the requirement states is in the spec, and the spec adds nothing the requirement does not state or plainly imply. Representation choices (a `Bool` flag for "logged in", cents for money, a list for a set) are fine. | "Name of the city; maximum 20 characters alphabetic string" → `o.valid = true ↔ 1 ≤ len ≤ 20 ∧ all isAlpha` (the `1 ≤` is a reasonable reading of "name") |
| `adds` | The spec states a condition, value or threshold the requirement does not (an invented bound, a hard-coded value, an extra precondition), and otherwise covers the requirement. | "detect consecutive failed login attempts" → `failedAttempts < 3` (the SRS gives no 3); "in dollars and cents" → `value ≤ 9999` |
| `omits` | A condition the requirement states is missing or not tied to the output, and nothing is added. Weak specs often land here. | "display the number of items in the cart, along with the total cost" → only `o.itemCount = …`, no total; "default = 1; maximum = stock" → only `1 ≤ q ≤ stock`, no default |
| `wrong` | The spec contradicts the requirement, constrains the wrong thing, or both adds and omits enough that it is a different requirement. Also: `post` cannot be satisfied for inputs the requirement allows. | login succeeds iff the input equals `"registeredUsername"`; a cart `add` whose `post` keeps the cart unchanged |

Tie-breaks: both adds and omits → `wrong` if the main rule is lost, else the larger defect. A requirement that is too
vague to formalise ("the system shall be user friendly") → `faithful` only if the spec states no more than the text;
an invented measurable threshold is `adds`.

**Agreement.** `python evaluation/kappa.py` prints Cohen's κ over the four labels and for faithful vs not, the
observed agreement and the confusion matrix (accepts `F/A/O/W`). With the columns blank it prints "not yet rated".
Report the faithful rate per strength class (weak / strong) next to κ; settle disagreements after κ is computed.

## 1. Grounding

`grounded(spec_code, entry, text)` in `evaluation/p8_grounding.py` is also the P11 grounding test
(`evaluation/strength_score.py` gives payoff 0 to an ungrounded spec).

Ungrounded by strength class: **strong 101 of 302 (33 %)**, weak 22 of 203 (11 %), copy-ok 2 of 12. Of the 231
ungrounded constants, 151 are strings, 78 numbers, 2 characters. So a large part of what the L0.5 checks call
*strong* is strong because of invented constants (hard-coded messages, credentials, thresholds) that a copy
implementation cannot reproduce: strength and fidelity are different properties, and the strong class should not be
read as "faithful".

Caveats: the rules accept a number that is a unit change or ± 1 of a stated number, so a
grounded spec can still use a stated number in the wrong place; and domain facts the SRS does
not state (a month has at most 12, an e-mail address has an `@`) count as ungrounded unless
the text names them. Read the list, not only the count.
