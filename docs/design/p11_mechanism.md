# P11: a payoff that rewards stronger contracts

Issue P11 (`docs/issues.tex`): a contract equal to the L0 conditions, or weaker, makes every proof
obligation easy, and nothing in the pipeline rewards a contract that says more. This note frames
the problem as a principal–agent problem, defines a payoff the harness can compute without a model,
and reports it on the stored specs (`evaluation/strength_score.py` →
`docs/analysis/strength_scores.md`). It is a **measurement**, not yet a training or selection signal.

## 1. Framing

| | who | wants | controls | observes |
|---|---|---|---|---|
| **principal** | the harness | a contract that says what the requirement says: satisfiable, rejects wrong behaviour, adds nothing the text does not state | the checks, the payoff, what is accepted | the Lean code, Lean's verdicts, the requirement text |
| **agent** | the model (Qwen) | to be accepted (it is prompted to pass the checks) | the text of `Input`/`Output`/`Spec` and the example | the prompt and the feedback |

The agent's cheapest strategy under the current acceptance rule (compiles + rejects one bad example
+ L0.5) is a *weak* contract: `post` that a copy-the-input implementation satisfies. It compiles,
its `example` is trivial, and every later obligation (PO1–PO3) becomes easy. 42 % of the v11 specs
are weak (P2). The principal cannot see "faithful to the requirement" directly (that needs a human,
P8); it can see proxies that are expensive to fake. The payoff below combines three hard gates with
one graded proxy.

## 2. The payoff

For a spec `S` with requirement text `T`:

```
payoff(S) = 0                           if S is unsatisfiable
          = 0                           if S is vacuous
          = 0                           if S is ungrounded in T
          = 0                           if S is untestable (no canonical example)
          = killed(S) / |M(S)|          otherwise  (mutant-kill rate, in [0, 1])
```

**Unsatisfiable.** The spec does not compile (so there is no Lean-checked
`example : Spec.pre i ∧ Spec.post i o`), or L0.5's output-mention check found a `post` conjunct that
only constrains the input and does not follow from `pre` (`l05.strength.output_free`): no
implementation can establish it.

**Vacuous.** `post` rejects none of the changed outputs on the example input (the L0.5 vacuity
check, with a larger mutant set).

**Ungrounded.** A constant in `Spec.pre`/`Spec.post` that the requirement does not contain: a number
≥ 2 that is not in the text (as digits or as a word), or a string literal that is not in the text.
The P8 check (`evaluation/p8_grounding.py`, `grounded(spec_code, entry)`) is used when it is present;
otherwise the script uses this local rule.

**Untestable.** The example is not in the `Spec.post {…} {…}` form, or no output field has a type
the harness can vary. The agent can always write the canonical form, so this costs it the payoff.

**Mutant set `M(S)`** (all generated by the harness, none by the model):

* *copy/constant mutants*: the copy-and-constant implementations of `chain_checks._candidates`
  (each output field = a same-typed input field or a constant; at most 48 combinations), evaluated
  on the example input and on up to 2 more inputs (single-field changes of the example input that
  Lean shows satisfy `pre`);
* *perturbation mutants*: the example output with one field (or one field of a nested record)
  changed: `Nat` ±1 and 0 (and L0.5's large value), `Bool` flipped, `String` `""` and a changed
  string, `List` emptied / doubled / first element dropped / one element added to an empty list,
  `Option` → `none`.

Mutants equal to the example output on the example input are dropped. A mutant `(i, m)` is
**killed** when Lean proves `¬ Spec.post i m` by `decide`. All mutants of a spec are checked in one
Lean run (one more run checks which extra inputs satisfy `pre`).

## 3. Incentive properties

1. **A stronger contract never scores lower on the same mutants.** If `post'` implies `post`, every
   mutant `post` rejects is rejected by `post'`, so `killed` can only grow. (Gates aside: a stronger
   `post` can become unsatisfiable, which costs everything; this is the intended trade-off.)
2. **Trivial contracts score 0.** `post := True` (or one that only restates `pre`) is vacuous.
3. **Unsatisfiable contracts score 0**, so strength cannot be bought with `False` or with
   input-only conditions. Without this gate, `post := False` would kill every mutant.
4. **A weak contract loses the copy mutants.** If a copy implementation satisfies `post` for every
   input, its outputs survive on every tested input; the kill rate is capped below 1 by the share of
   copy mutants. Moving the copy witness into the example (choosing an example output that equals the
   copy) does not help: the same copy implementation is run on the extra inputs (when the harness
   finds inputs that satisfy `pre`; otherwise this protection is lost, see Limits).
5. **Invented constants are not free.** Over-specifying (an invented limit, a UI message the text
   never gives) would kill more mutants; the grounding gate makes it cost the whole payoff. This is
   the main defence against "stronger than the requirement".
6. **Cheap to compute, not model-graded.** Two Lean runs per spec, no model call, deterministic:
   the agent cannot argue with the principal.

## 4. Limits

* **Kill ≠ wrong.** A mutant is generated, not known to be wrong. A copy output can be the correct
  answer on some input (an echo requirement), and a perturbed output can also be correct (two valid
  answers). The score rewards rejecting them anyway. This is why it is a strength proxy, not a
  correctness score; requirements tagged `copy-ok` should be read apart.
* **Concrete inputs only.** Mutants are checked on at most three inputs. A `post` that is weak only on
  other inputs is not caught; `chain_checks.trivial_witness` (universally quantified) is the stronger
  check for copy-satisfiability and is reported as `l05.strength.class`.
* **`decide` must evaluate.** A conjunct that `decide` cannot evaluate (undecidable instance, large
  lists) leaves the mutant unkilled, which under-scores the spec.
* **Grounding is lexical.** Unit conversions (30 minutes → 1800 s), derived numbers and paraphrased
  messages are flagged as ungrounded; synonyms of a string are not. The gate is deliberately strict and
  its false positives are listed in the report.
* **Mutant set bias.** Specs with more output fields get more mutants; the rate normalises the count,
  but the difficulty of the mutants differs between specs. Scores compare specs of one requirement
  (e.g. two attempts, two models) better than specs of different requirements.
* **Not semantic.** A contract can be strong, grounded and still say something other than the
  requirement. P8's hand review remains the ground truth.

## 5. How it would be used

* **Now: reported** per spec and per SRS (`docs/analysis/strength_scores.md`) next to the L0.5 class,
  so a run that verifies more specs by weakening them is visible.
* **Next (not built):** as a tie-breaker in `generate_verified` when several attempts pass the checks
  (keep the highest payoff), and as a gate before L1 (payoff 0 → the spec is sent back with the
  reason). Both change what reaches L1/L2 and need a 3-seed comparison (`compare_runs.py`) before
  they become defaults.
* **Not:** a reward for fine-tuning. The mutant set is fixed and known, so an optimiser would learn
  to kill exactly these mutants (Goodhart). It would need held-out mutant families first.
